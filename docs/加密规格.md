# NyaPassword 加密规格

> 规格 v1，对应 `npw-crypto`（common 仓库 `crates/npw-crypto`）。本文描述**代码实际的行为**，所有常量都以代码为准；与 [设计方案.md](设计方案.md) §4 有出入时以本文为准。测试向量见 §12。
> 本文中的域名、地址、账号一律是占位值（`example.com`、`203.0.113.x`）。

本文回答“另一个实现要和 NyaPassword 逐字节互通，需要知道什么”。条目明文的结构见 [条目格式.md](条目格式.md)，服务端接口见 [API.md](API.md)，攻击面分析见 [威胁模型.md](威胁模型.md)，原生加密导出见 [导出格式.md](导出格式.md)。

## 0. 约定

| 项 | 约定 |
|---|---|
| 二进制值在 JSON / API 中 | base64url，**无填充**（`npw_crypto::b64`）。解码（`unb64`）先去首尾空白和末尾 `=`，URL 安全字母表失败时再试标准字母表（兼容导入数据） |
| 哈希、摘要、测试向量中的二进制值 | 小写 hex |
| UUID 进入 AAD 时 | UUID 字符串对应的 16 个原始字节（RFC 9562 的大端字节序，即 `Uuid::as_bytes()`） |
| 整数进入 AAD 时 | 大端 |
| `‖` | 字节串拼接 |
| 随机数 | 操作系统 CSPRNG（`rand::rngs::OsRng`；WASM 上 `getrandom` 的 `js` 后端，即 `crypto.getRandomValues`） |
| 密钥在内存中 | `Key32` / `SecretKey` 实现 `Zeroize` + `ZeroizeOnDrop`，`Debug` 不打印内容；派生中间值用完即清零 |

## 1. 原语与库

只使用审计过的现成实现，`npw-crypto` 只固定参数、字节布局和域分隔。

| 用途 | 算法 | crate（Cargo.lock 中的版本） |
|---|---|---|
| 主密码拉伸 | Argon2id，版本 0x13 | `argon2` 0.5.3 |
| 子密钥派生 | HKDF-SHA256（RFC 5869） | `hkdf` 0.12.4、`sha2` 0.10 |
| 对称加密 | XChaCha20-Poly1305（24 字节 nonce，16 字节标签） | `chacha20poly1305` 0.10.1 |
| 账户密钥对 | X25519 | `x25519-dalek` 2.0.1 |
| 登录 | OPAQUE（RFC 9807），见 §7 | `opaque-ke` 3.0.0（`voprf` 0.5.0） |
| Unicode 规范化 | NFKD | `unicode-normalization` 0.1.25 |
| 服务端备份 | age（X25519 接收者）、zstd、tar | `age` 0.11.5、`zstd` 0.13.3、`tar` 0.4.46 |

设计方案 §4.6 提到的 `hpke` 目前**没有**引入：共享保险库尚未实现，见 §4.3。

## 2. 主密钥派生（`kdf.rs`）

### 2.1 公式

```text
P     = UTF-8( NFKD(主密码) )                                  不去首尾空白，不改大小写
K_pw  = Argon2id(password = P, salt = account_salt,
                 m = kdf.m KiB, t = kdf.t, p = kdf.p,
                 version = 0x13, 无 secret、无 associated data, 输出 32 字节)
K_sk  = HKDF-SHA256(salt = account_salt, IKM = Secret Key 原始 16 字节, info = "npw/sk/v1", L = 32)
M     = K_pw XOR K_sk                                          32 字节
AUK   = HKDF-SHA256(salt = 无, IKM = M, info = "npw/auk/v1",    L = 32)   账户解锁密钥
LOGIN = HKDF-SHA256(salt = 无, IKM = M, info = "npw/opaque/v1", L = 32)   OPAQUE 的“密码”
```

- “salt = 无”按 RFC 5869 即 32 个零字节（`Hkdf::new(None, …)`）。
- 所有 info 字符串都是 ASCII，不带结尾 NUL。
- `account_salt` 至少 16 字节，否则 `InvalidKdfParams`。客户端注册时生成 **16 字节**随机盐；**改主密码时会生成新盐**（`npw-core` `change_password`），KDF 参数同时重置为默认值。
- 只知道主密码（没有 Secret Key）或只知道 Secret Key（没有主密码）都得不到 M；拿到服务器数据库或备份的攻击者没有 128 位的 Secret Key，无法离线暴力破解主密码（§7.3）。

### 2.2 参数（`KdfParams`）

JSON 形式（API、账户状态、导出文件头都用它）：

```json
{ "alg": "argon2id", "m": 65536, "t": 3, "p": 4 }
```

| 键 | 含义 | 默认 | `validate()` 接受的范围 |
|---|---|---|---|
| `alg` | 只有 `argon2id` | `argon2id` | — |
| `m` | 内存，KiB | 65536（64 MiB） | 16384 ≤ m ≤ 1048576（16 MiB – 1 GiB） |
| `t` | 迭代次数 | 3 | 1 ≤ t ≤ 64 |
| `p` | 并行度（lanes） | 4 | 1 ≤ p ≤ 16 |

- `derive_master` 本身**不**检查范围（只检查盐长和 Argon2 自身的合法性）。参数来自服务器时必须先 `validate()`：`npw-core` 在登录（`prelogin` 返回的参数）和每次解锁前都校验；服务端在注册和改密码时校验。两处都有只供测试用的开关 `allow_weak_kdf`（客户端 `ClientConfig`；服务端 `Config` 中标了 `serde(skip)`，配置文件和环境变量都设置不了）。
- 下限防的是恶意服务器把参数降到可以快速暴力破解；上限防的是让客户端分配巨量内存。
- `KdfParams::insecure_for_tests()` = `m=64, t=1, p=1`，永远通不过 `validate()`。

### 2.3 恢复码（预留）

```text
AUK_r   = HKDF-SHA256(salt = account_salt, IKM = 恢复码 32 字节, info = "npw/recovery-auk/v1",    L = 32)
LOGIN_r = HKDF-SHA256(salt = account_salt, IKM = 恢复码 32 字节, info = "npw/recovery-opaque/v1", L = 32)
```

恢复码是 256 位随机数，不需要 Argon2。`derive_recovery`、AAD `npw/recovery-account-key/v1`、API 类型、数据库列和登录方式 `recovery_code` 都已存在，但**设置恢复码的端点没有实现**（见 [API.md](API.md) §12）。注意 `account_salt` 会在改主密码时更换，实现恢复码时要么改用独立的盐，要么在改密码时重新封装恢复用的 AK。

## 3. Secret Key（`secret_key.rs`）

128 位随机数，在注册的设备上生成（`SecretKey::generate`），**从不发送给服务器**，打印在紧急恢复包里，新设备首次登录时输入一次。

### 3.1 文本形式

```text
A1-XXXXXX-XXXXX-XXXXX-XXXXX-XXXXX-C          共 35 个字符
```

- `A1`：格式版本。
- 26 个 Crockford Base32 字符，字母表 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`（没有 I、L、O、U）：把 16 字节按大端视为 128 位，后面补 2 个 0 位凑成 130 位，每 5 位一个字符。最后一个字符的低 2 位就是这 2 个补位。分组 6-5-5-5-5。
- `C`：校验字符 = 字母表[ SHA-256(`"A1"` ‖ 原始 16 字节)[0] & 31 ]。随机的单字符抄写错误有 31/32 的概率被发现。

例：原始字节 `4e796150617373776f72642d534b2d31`（ASCII `NyaPassword-SK-1`）→ `A1-9SWP2M-31EDS-QEVVJ-CGPN6-JSD64-7`。

### 3.2 解析规则（`SecretKey::parse`）

1. 去掉所有空白字符和 `-`，转大写；
2. 必须以 `A1` 开头，之后恰好 27 个字符（26 个数据 + 1 个校验）；
3. 每个字符（包括校验字符）先做替换 `O→0`、`I→1`、`L→1`，再查字母表；查不到即错误（如 `U`）；
4. 最后一个数据字符的低 2 位必须为 0；
5. 重新计算校验字符，必须相等。

任何一步失败都是 `InvalidSecretKey`（附带英文原因，原因文字不属于格式）。

### 3.3 在设备上的保存

Secret Key 原始 16 字节用**设备密钥**（各端宿主提供的 32 字节密钥）加密后存在本地副本里：`envelope::seal(设备密钥, raw, aad::device_secret("secret_key"))`；会话令牌同样（`device_secret("session")`）。设备密钥的保管方式各端不同：

| 端 | 设备密钥在哪 |
|---|---|
| 桌面（`desktop/src-tauri/src/device_key.rs`） | 系统凭据存储（Windows 凭据管理器 / macOS 钥匙串 / Secret Service）；不可用时退回到数据目录下的 `device-key.bin`（只受文件权限保护，界面会提示） |
| Android（`android/.../core/Keys.kt` `DeviceKey`） | `noBackupFilesDir` 下的文件，用 Android Keystore 中不要求用户认证的 AES-GCM 密钥包装（只把文件绑定到本机） |
| 浏览器扩展、网页版（`common/web/src/lib/bridge-wasm.ts`） | IndexedDB 中的明文 `device_key`，与本地副本放在一起：只防“副本文件被单独拷走”，不防拿到整个浏览器配置目录的人（见威胁模型） |

## 4. 密钥层级

```text
主密码 ─NFKD─► Argon2id ─┐
                          ├─ XOR ─► M ─HKDF─┬─► AUK ──解密──► AK（账户密钥）
Secret Key ───► HKDF ─────┘                 └─► LOGIN（OPAQUE）
AK ─┬─► 账户 X25519 私钥
    └─► VK（每个保险库）─┬─► 保险库元数据
                         └─► IK（每个条目）─┬─► 条目内容
                                            └─ 条目内容里存着 FK（每个附件）─► 附件分块
```

### 4.1 每把密钥

| 密钥 | 长度 | 产生 | 如何保存（信封 = §5） | AAD（§6） | 存放位置 |
|---|---|---|---|---|---|
| AUK | 32 | 每次解锁派生 | 不保存 | — | 只在内存 |
| LOGIN | 32 | 同上 | 解锁期间留在内存，用于会话过期后静默重新登录 | — | 只在内存 |
| AK | 32 | 注册时随机 | `encrypted_account_key = seal(AUK, AK)` | `account_key(account_id)` | 服务端 `accounts.encrypted_account_key`；本地账户状态 |
| X25519 私钥 | 32 | 注册时随机 | `encrypted_private_key = seal(AK, sk)`；公钥 32 字节原样 base64url | `account_private_key(account_id)` | 服务端 `accounts` |
| VK | 32 | 建保险库时随机 | `wrapped_key = seal(AK, VK)` | `vault_key(vault_id)` | 服务端 `vault_members.wrapped_key`（每个成员一份） |
| 保险库元数据 | — | — | `encrypted_meta = seal(VK, JSON)`，JSON 为 `{"name": "个人", "icon": "", …}`，未知键保留 | `vault_meta(vault_id)` | 服务端 `vaults.encrypted_meta` |
| IK | 32 | 新建条目时随机；之后的修订**沿用**同一把 | `wrapped_key = seal(VK, IK)` | `item_key(vault_id, item_id)` | 每个修订一份，`item_revisions.wrapped_key` |
| 条目内容 | — | — | `ciphertext = seal(IK, 条目 JSON)` | `item_content(vault_id, item_id, format_major)` | `item_revisions.ciphertext` |
| FK | 32 | 每个附件随机 | 不单独封装：base64url 写在条目内容 `attachments[].key` 里，随条目内容一起被 IK 加密 | — | 条目内容 |
| 附件内容 | — | — | `stream::encrypt(FK, 文件)`（§8） | `attachment(attachment_id)` | 服务端 `data/attachments/<id>` |

- **改主密码**：新盐、新参数（默认值）、新 AUK，重新封装同一个 AK，重新做一次 OPAQUE 注册；AK、VK、IK、条目都不动。服务端删除该账户其他设备的会话。
- **移动条目到其他保险库**（预留能力）：IK 的 AAD 含保险库 ID，所以要用新 VK 重新封装 IK，内容的 AAD 也含保险库 ID，所以内容也要重新加密。
- `unlock_with_key`（快速解锁）拿到一个候选 AK 后，用它打开 `encrypted_private_key` 来证明它是对的。

### 4.2 快速解锁（各端）

`Client::quick_unlock_key()` 只在已解锁时把 AK 交给宿主，宿主自己保管：

| 端 | 方式 |
|---|---|
| 桌面 Windows（`desktop/src-tauri/src/quick_unlock.rs`） | Windows Hello 密钥对随机 32 字节挑战签名；包装密钥 = HKDF-SHA256(salt = 挑战, IKM = 签名, info = `"npw/desktop/quick-unlock/v1"`)；`seal(包装密钥, AK, aad::quick_unlock(account_id))` 存入 `quick-unlock.json`。只在本次运行已用主密码解锁过、且距上次主密码解锁不到 14 天时可用 |
| Android | Keystore 中 `setUserAuthenticationRequired(true)`、`setInvalidatedByBiometricEnrollment(true)` 的密钥包装 AK |
| 浏览器扩展 | AK 以 base64url 放在 `chrome.storage.session`（只在内存，浏览器关闭即失效），Service Worker 被回收后从这里恢复 |

### 4.3 为共享预留

每个账户注册时就生成 X25519 密钥对（`AccountKeyPair`），`vault_members` 表按（保险库, 账户）存各自封装的 VK 和角色。共享时计划用 HPKE 把 VK 封装给成员公钥；v1 没有实现，`vault_members` 里只有 `owner` 一行。

## 5. 密文信封（`envelope.rs`）

除附件外，所有对称加密都用同一种信封：

```text
偏移  长度      内容
0     1        version   = 1
1     1        algorithm = 1（XChaCha20-Poly1305）
2     24       nonce（随机）
26    n + 16   XChaCha20-Poly1305(key, nonce, plaintext, AAD) 的密文 ‖ 16 字节标签
```

| 常量 | 值 |
|---|---|
| `VERSION` | 1 |
| `ALG_XCHACHA20POLY1305` | 1 |
| `HEADER_LEN` | 26 |
| `OVERHEAD` | 42（空明文的信封长度） |

- 版本和算法字节**不**在 AAD 里，但改动它们只会让解析换一条路（新的版本 / 算法号会有自己的格式），当前实现遇到别的值直接拒绝。
- 192 位随机 nonce，同一把密钥可以安全地加密任意多条消息。
- 新算法只会获得新的编号（附件流已占用 2），旧编号永久可解。
- 封装 32 字节密钥（`wrap_key`）得到 74 字节的信封。

`open` 的检查顺序与错误：

| 情况 | 错误 |
|---|---|
| 长度 < 42 | `Malformed` |
| 第 0 字节 ≠ 1 | `UnsupportedVersion(v)` |
| 第 1 字节 ≠ 1 | `UnsupportedAlgorithm(a)` |
| 认证失败（密钥错、AAD 错、任何字节被改） | `Decrypt`（故意不带细节） |

`seal_with_nonce` 只用于生成测试向量和兼容样例，产品代码只用随机 nonce 的 `seal`。

## 6. 关联数据（AAD，`aad.rs`）

每个信封都绑定到“它是什么、属于谁”：恶意服务器无法把一个条目的密文换成另一个条目的、搬到另一个保险库、或把账户密钥当条目密钥呈现。布局一律是：

```text
ASCII 域标签 ‖ 若干个 16 字节原始 UUID ‖ 尾部（大端整数或名字）
```

各部分之间**没有**长度前缀或分隔符：没有哪个标签是另一个标签的前缀，标签之后的 UUID 定长，所以不同用途的 AAD 不会相同。

| 函数 | 标签 | 之后 | 用于 |
|---|---|---|---|
| `account_key(account_id)` | `npw/account-key/v1` | account_id | AUK 封装 AK |
| `account_private_key(account_id)` | `npw/account-x25519/v1` | account_id | AK 加密 X25519 私钥 |
| `recovery_account_key(account_id)` | `npw/recovery-account-key/v1` | account_id | 恢复码密钥封装 AK（预留） |
| `vault_key(vault_id)` | `npw/vault-key/v1` | vault_id | AK 封装 VK |
| `vault_meta(vault_id)` | `npw/vault-meta/v1` | vault_id | VK 加密保险库元数据 |
| `item_key(vault_id, item_id)` | `npw/item-key/v1` | vault_id ‖ item_id | VK 封装 IK |
| `item_content(vault_id, item_id, format_major)` | `npw/item/v1` | vault_id ‖ item_id ‖ format_major（u16 大端，2 字节） | IK 加密条目内容 |
| `attachment(attachment_id)` | `npw/attachment/v1` | attachment_id | 附件流的每一块 |
| `device_secret(name)` | `npw/device-secret/v1/`（注意结尾斜杠） | name 的 UTF-8 | 设备密钥加密的本地秘密：`secret_key`、`session`；服务端用 `server.key` 加密配置时也用它：`backup_settings`、`target:<目标 ID>` |
| `quick_unlock(account_id)` | `npw/quick-unlock/v1` | account_id | 快速解锁包装 AK |
| `export(export_id)` | `npw/export/v1` | export_id | 原生导出（见导出格式.md，载荷 AAD 还附加文件头行的 SHA-256） |

`format_major` 绑定进条目内容的 AAD，所以密文不能被改标成别的格式大版本。条目的 `format_major` 取 `max(条目 format 的 MAJOR, 当前客户端的 FORMAT_MAJOR)`（`npw_model::format::format_major_of`），并作为明文字段随修订一起交给服务端，解密时由客户端用它重建 AAD。

**不在任何 AAD 里的**：修订号、`seq`、回收站标志 `deleted`、时间、设备 ID。这些是服务端掌管的元数据，恶意服务器可以改，后果见威胁模型 §3.3。

例：`item_content(0192f0c0-0000-7000-8000-000000000002, 0192f0c0-0000-7000-8000-000000000064, 1)` =

```text
6e70772f6974656d2f7631                        "npw/item/v1"
0192f0c0000070008000000000000002              vault_id
0192f0c0000070008000000000000064              item_id
0001                                          format_major = 1
```

## 7. OPAQUE（`opaque.rs`）

### 7.1 配置

```rust
impl opaque_ke::CipherSuite for Suite {
    type OprfCs = opaque_ke::Ristretto255;          // OPRF：ristretto255-SHA512
    type KeGroup = opaque_ke::Ristretto255;         // AKE 群：ristretto255
    type KeyExchange = TripleDh;                    // 3DH，哈希 SHA-512
    type Ksf = opaque_ke::ksf::Identity;            // 不做密钥拉伸
}
```

- 这正是 opaque-ke 自带 RFC 测试向量中的 `Ristretto255Sha512NoKsf` 组合。
- OPAQUE 的“密码”是 §2 的 **LOGIN**（32 字节高熵），昂贵的 Argon2id 已经在客户端做过，所以 KSF 用恒等函数。
- 凭据标识（credential identifier）= account_id 的 16 个原始字节（注册、登录、改密码都一样）；未知登录名用服务端为它伪造的 account_id（§10.2）。
- 客户端 / 服务端身份、上下文都用 opaque-ke 的默认值（不额外传）。OPAQUE 产生的会话密钥 / export key **没有使用**：登录成功后服务端签发普通的 bearer 令牌。
- 消息在 API 中是 opaque-ke `serialize()` 的字节，base64url。

### 7.2 流程

| 步骤 | 客户端 | API | 服务端 |
|---|---|---|---|
| 注册 1 | `client_register_start(LOGIN)` | `POST /v1/auth/register/start` | `server_register_start(setup, request, account_id)` |
| 注册 2 | `client_register_finish(state, LOGIN, response)` → upload | `POST /v1/auth/register/finish` | `server_register_finish(upload)` → 存为 `accounts.opaque_record` |
| 登录 1 | `client_login_start(LOGIN)` | `POST /v1/auth/login/start` | `server_login_start(setup, record 或 None, request, account_id)`，状态存 `login_attempts`（5 分钟，一次性） |
| 登录 2 | `client_login_finish(state, LOGIN, response)` → finalization；**密码、Secret Key 或服务端记录任何一个不对都在这里失败**，三者不可区分 | `POST /v1/auth/login/finish` | `server_login_finish(state, finalization)` 成功才签发会话 |
| 改密码 | 同注册，用新 LOGIN | `POST /v1/account/password/{start,finish}` | 覆盖 `opaque_record` |

服务端的长期 OPAQUE 密钥材料 `ServerSetup` 在首次启动时生成，base64url 存在数据库 `settings` 表的 `opaque_setup` 里（因此也在备份里）。

### 7.3 为什么服务器拿不到可离线验证的东西

- 服务端只存 OPAQUE 注册记录，登录全程不传输任何密码等价物；登录成功同时向客户端证明服务端持有注册时的记录。
- 即使攻击者同时拿到 `ServerSetup`（OPRF 密钥）和注册记录，能做的离线猜测对象也是 LOGIN，而 LOGIN 含 128 位 Secret Key 的熵，无法穷举。
- 未知账户：`server_login_start` 传 `None`，opaque-ke 用 `ServerSetup` 里的伪造参数生成看起来真实的响应，登录接口不能用来探测账户是否存在。

## 8. 附件分块加密（STREAM，`stream.rs`）

```text
头部：  [version = 1][algorithm = 2][nonce 前缀：19 字节随机]          共 21 字节
第 i 块：XChaCha20-Poly1305(FK, nonce_i, 明文块 i, AAD)                 每块附 16 字节标签
nonce_i = 前缀(19) ‖ i（u32 大端，4 字节）‖ 末块标志（最后一块 1，其余 0；1 字节）
AAD     = aad::attachment(attachment_id)（每块相同）
```

| 常量 | 值 |
|---|---|
| `VERSION` | 1 |
| `ALG_XCHACHA20POLY1305_STREAM` | 2 |
| `CHUNK` | 1048576（1 MiB 明文） |
| `HEADER_LEN` | 21 |

- 除最后一块外每块恰好 1 MiB 明文（密文 1048592 字节）；最后一块可以更短。
- 空文件 = 一个空的最后块（只有标签），共 37 字节。
- 长度恰好是 1 MiB 整数倍时**不**追加空块：最后一个满块就是末块。
- 密文长度 `encrypted_len(n) = 21 + n + 16 × max(1, ⌈n / 1 MiB⌉)`。
- 解密：头部之后按 1048592 字节切块，最后剩下的部分是末块（至少 16 字节）。块序号防重排，末块标志防截断和追加，AAD 防止把一个附件的块拿去冒充另一个附件。
- 错误：总长 < 37 或某块 < 16 字节 → `Malformed`；版本 ≠ 1 → `UnsupportedVersion`；算法 ≠ 2 → `UnsupportedAlgorithm`；任何块认证失败 → `Decrypt`。
- 另有完整性检查：条目内容 `attachments[].blob_sha256` 记录整个加密 blob 的 SHA-256（hex），客户端下载后先比对；服务端上传时计算并返回同一个值，客户端比对后才把附件加进条目。
- 当前实现整体读入内存再加解密（附件上限默认 100 MiB，服务端 `max_attachment_mb`）；格式本身支持流式。

## 9. 会话、邀请码与服务端秘密

这些不涉及条目数据的保密，但同样固定了格式：

| 项 | 规格 |
|---|---|
| access token | 32 字节随机，base64url；有效 1 小时 |
| refresh token | 32 字节随机，base64url；有效 30 天；**一次性**（每次刷新换新的一对） |
| 令牌在服务端 | 只存 SHA-256(令牌字符串) 的 hex（`sessions.token_hash`） |
| 邀请码 | 10 字节随机 → RFC 4648 Base32 的前 16 个字符，写成 `XXXXXXXX-XXXXXXXX`；有效 1–720 小时；服务端只存 SHA-256(邀请码字符串) |
| 管理口令 | Argon2 PHC 字符串（`argon2` crate 默认参数：Argon2id、m=19456 KiB、t=2、p=1），至少 12 个字符 |
| 管理 TOTP | 20 字节随机密钥，SHA-1、6 位、30 秒，接受前后各一个时间步 |
| 管理会话 | 32 字节随机，服务端内存中存哈希，12 小时，重启即失效 |
| `server.key` | 数据目录下的 JSON：`{"secret": <32 字节 base64url>, "age_identity": "AGE-SECRET-KEY-1…", "created_at": …}`，Unix 上权限 0600 |

`server.key` 的 `secret` 用来：①用信封 + `device_secret(name)` 加密数据库里的备份设置和备份目标密钥；②给未知登录名生成稳定的伪造 prelogin 应答：

```text
out        = HMAC-SHA256(secret, "npw/fake-prelogin/v1" ‖ lowercase(trim(login)))
account_id = out[0..16]，把版本位设成 7、变体位设成 RFC 9562（看起来像 UUIDv7）
salt       = base64url(out[16..32])
kdf        = KdfParams::default()
```

## 10. 内容哈希与保险库摘要（`npw-api`）

```text
item_hash   = hex( SHA-256( wrapped_key 字节 ‖ ciphertext 字节 ) )
vault_digest = hex( SHA-256( 按 item_id 字符串升序，逐个拼接：
                 item_id（UTF-8）‖ 0x00 ‖ revision（i64 大端 8 字节）‖ deleted（1 字节 0/1）‖ item_hash（hex ASCII） ) )
```

服务端在写入时计算 `item_hash`，客户端拉取时重算比对（不一致即视为传输损坏）。摘要的用途见 [API.md](API.md) §6.3、§6.6。哈希是对**密文**算的，不依赖 JSON 规范化。

## 11. 服务端备份（`npw-backup`）

```text
backups/nyapassword-<YYYYMMDDTHHMMSSZ>-s<最大 seq，9 位补零>.tar.zst.age
= age 加密（X25519，接收者 = 服务端自己的 age 公钥 + 设置里的离线公钥 age1…）
    zstd（级别 9）
      tar（GNU 头，每个文件 mode 0600，mtime = created_at / 1000）
        manifest.json   总是第一个
        db.sqlite3      VACUUM INTO 得到的一致快照
        server.key      §9
attachments/<attachment_id>   附件 blob 原样上传（本来就是端到端加密的 STREAM 密文，不再套 age），每个目标只传一次
```

`manifest.json`（`serde_json::to_vec_pretty`）：

```json
{
  "format": 1,
  "created_at": 1759536000000,
  "server_version": "0.1.0",
  "epoch": "<数据库 epoch>",
  "accounts": 1, "items": 120, "revisions": 340, "attachments": 3,
  "vaults": { "<vault_id>": 57 },
  "files": { "db.sqlite3": "<hex SHA-256>", "server.key": "<hex SHA-256>" }
}
```

- 打开时（`npw_backup::open`）：age 解密 → zstd 解压 → 解 tar → `format` 必须是 1 → `files` 里列出的每个文件必须存在且 SHA-256 一致；解包到目录时拒绝含 `..`、`/`、`\` 的文件名。
- 没有接收者时拒绝加密。
- 谁能解开备份：持有服务端 age 私钥（在 `server.key` 里，也在每个备份里）或离线私钥（紧急恢复包）的人。解开后得到的是数据库（条目仍是密文，OPAQUE 记录见 §7.3）和 `server.key`。
- 保留（祖父-父-子）、防删模式、演练、告警见设计方案 §8 和 [API.md](API.md) §10。
