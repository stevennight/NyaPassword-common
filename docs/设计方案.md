# NyaPassword 设计文档

> 状态：草案 v0.1（2026-10-04）。开发计划见 [开发计划.md](开发计划.md)，界面原型见 [prototype.html](prototype.html)。
> 规格（以代码为准，与本文有出入时以规格为准）：[加密规格.md](加密规格.md)、[条目格式.md](条目格式.md)、[API.md](API.md)、[威胁模型.md](威胁模型.md)、[导出格式.md](导出格式.md)。
> 本文中的域名、地址、账号一律是占位值（`example.com`、`203.0.113.x`）。

自建、自研的密码管理器：服务端为准、各端（Windows / 浏览器扩展 / Android，以后 macOS / Linux / iOS）保留本地加密副本；支持自动填充、通行密钥（passkey）、TOTP、SSH 密钥；服务端自带自动备份到对象存储；可从 Bitwarden / 1Password 迁移。界面参考 1Password。

## 0. 对最初想法的评估（结论先行）

| 想法 | 结论 | 调整 / 补充 |
|---|---|---|
| 自研，各端同步，自动填充、passkey、TOTP、SSH | **可行**。真正的难点是两件事：①加密与数据格式一旦出错就是丢密码；②自动填充的兼容性（网页千奇百怪、Android 各 ROM 差异）要长期打磨 | 只用审计过的密码学库，不自己写原语；**所有端共用同一个 Rust 核心**（加密、数据模型、同步、合并、网址匹配、导入导出全在里面），各端只写界面和系统集成。这是 1Password 和 Bitwarden 现在的做法，能从根上消除“各端行为不一致把数据弄乱” |
| 服务端为主、客户端本地副本为辅 | **合理**，Bitwarden / 1Password 也是这样 | 两点澄清：①“服务端为主”指服务端决定**顺序和历史**，但只存密文，看不到任何明文（端到端加密）；②离线时仍然要能**新建和修改**（比如在只有内网的地方注册账号），所以冲突不会消失，只是变少。用“每条目修订号 + 乐观并发 + 字段级三方合并 + 冲突两份都保留”处理，**任何情况下都不丢数据**（§7） |
| 一条一条、一个字段一个字段地存，而不是一个大文件 | **方向对**，不用 KDBX 做服务端格式的判断也对 | 三个粒度分开：**加密和存储以“条目”为单位**（一个条目一个密文，每次修改追加一个修订）；**合并以“字段”为单位**（字段有稳定 ID，在客户端解密后合并）。不按字段分别加密：服务端看不懂内容，字段级加密只会泄露“有几个字段、改了哪个”，还可能出现半个条目更新成功的撕裂状态。KDBX 不做存储格式，但做**导出格式**——这是“我的软件哪天坏了也能用 KeePassXC 打开”的逃生通道（§8.6） |
| 服务端自动备份到 OSS 等云服务 | **强烈同意**，而且应当是一等功能 | 备份内容本来就是密文，再加一层 age 加密；对象存储用**只写不删**的凭据 + 版本控制 / WORM 防误删防勒索；**自动恢复演练**（不是只看上传成功）；失败告警；多目标（阿里云 OSS + WebDAV）。另外客户端定期导出一份离线加密副本，不依赖服务端（§8） |
| 迁移支持 Bitwarden、1Password | 同意 | 你写的 `bw2op` 已经摸清了 Vaultwarden 导出 zip 的结构和各字段映射，直接移植到 Rust 导入器。并且**Bitwarden 的 passkey 可以迁过来**（JSON 导出里带私钥，1Password 收不了，我们能收）。1Password 用 `.1pux`。所有导入先预览、出报告、可整批撤销（§9） |
| Android 上从系统 / 其他密码管理器直接迁移 | **不做**（已确认） | 这是 FIDO 的 Credential Exchange（CXP / CXF）协议，Android 的接口还比较新、国内 ROM 支持情况不明，且只在迁移时用一次。从 Bitwarden 迁移用电脑端导入导出文件就能拿到全部内容（含附件和 passkey），不需要它 |
| 各端兼容是最大难点 | 同意 | 共用核心解决“数据层一致”；“系统集成层”的差异逐端列清单、建测试矩阵（§10、§11） |

### 0.1 额外建议

1. **先把现在的 Vaultwarden 备份起来**，不要等这个项目做完（它至少要几个月）。最简单：每天 `sqlite3 db.sqlite3 ".backup ..."` + 打包 `attachments/`、`rsa_key*`、`config.json` → 加密 → rclone 传到 OSS。临时用现成的 vaultwarden-backup 镜像也可以。
2. **双密钥派生（主密码 + Secret Key）**：账户密钥由“主密码”和设备上保存的 128 位随机“Secret Key”共同派生（1Password 的 2SKD）。服务器数据库或备份泄露时，攻击者没有 Secret Key 就无法离线暴力破解主密码。自建在 VPS 上、备份放在第三方云上，这层尤其值得（§4）。
3. **紧急恢复包（Emergency Kit）**：一张可打印的 PDF：服务器地址、账号、Secret Key、恢复码、备份解密私钥。注意**不能只存在这个密码库里**（循环依赖：密码库没了就拿不到解开备份的钥匙）。
4. **双轨运行**：新系统稳定前和 Vaultwarden 并行使用至少一个月，确认无误再切换。
5. **服务端自带网页版**：任何电脑上用浏览器就能临时访问，也是管理后台（备份、设备、日志）。

## 1. 目标与非目标

### 目标
- 个人使用，自建一个服务端（Docker 部署）。v1 **只做单账户**，但密钥层级、数据表、API 都按“多账户 + 共享保险库”设计（§4.2），以后加家庭共享不用迁移数据。
- 端到端加密：服务端和备份只有密文；服务端被攻破也拿不到明文。
- 数据不丢：服务端只追加修订、冲突两份都留、回收站、自动备份 + 恢复演练、客户端离线导出。
- 各端：桌面（Windows 为主；macOS、Linux 同时构建，但未经实机测试）、浏览器扩展（Chromium 内核：Chrome、Edge）、Android、网页版。
- 功能对齐 1Password / Bitwarden 的常用部分，清单见 §1.1。

### 非目标（不做，或有需要再说）
- 家庭共享 / 多账户（预留，不实现）、多租户 / 企业功能。
- Firefox 扩展（WXT 本身支持，以后有需要再加构建目标）。
- Android 上通过 CXP 从其他密码管理器直接迁移（电脑端文件导入已覆盖）。
- iOS、鸿蒙 NEXT（不运行 APK）。
- 服务端非 Docker 部署（二进制本身能跑，但不提供安装包和文档）。
- 通过无障碍服务（Accessibility）做 Android 自动填充：安全性差、易被商店下架。

### 目标环境
| 端 | 最低版本 | 说明 |
|---|---|---|
| 服务端 | Docker（linux/amd64、linux/arm64） | 单二进制 + SQLite，Caddy 负责 TLS |
| Windows | Windows 10 21H2+ / 11 | 主力平台，全部功能实机测试 |
| macOS | 13+（Apple Silicon、Intel） | 构建并发布，未经实机测试（标注“实验性”） |
| Linux | Ubuntu 22.04+ 等（AppImage、deb） | 同上 |
| 浏览器 | Chrome / Edge 120+（MV3） | 其他 Chromium 内核浏览器理论上可用 |
| Android | 8.0（API 26，自动填充框架） | 凭据提供程序（passkey）需 14（API 34）；内联建议需 11 |

## 2. 总体架构

```
                         ┌──────────────── 服务端（server 仓库） ────────────────┐
                         │  HTTPS API (axum) ─ OPAQUE 登录 ─ 同步 ─ WebSocket 推送 │
                         │  SQLite（只追加修订） ─ 附件 blob（内容寻址）           │
                         │  备份调度 → age 加密 → 阿里云 OSS / WebDAV               │
                         │  网页版 + 管理后台（嵌入 common/web 构建产物）           │
                         └───────────────▲───────────────────────────────────────┘
                                         │ 只有密文
     ┌────────────────────┬──────────────┼───────────────┬────────────────────┐
     │ desktop（Tauri 2） │ chrome（MV3 扩展）│ 网页版          │ android（Kotlin）   │
     │ Win / macOS / Linux│ Chrome / Edge    │                │                    │
     │ Svelte 界面         │ Svelte 弹窗/内联菜单│ Svelte 界面     │ Compose 界面        │
     │ ── Tauri 命令 ──    │ ── wasm-bindgen ─ │ ── wasm ──      │ ── UniFFI ──        │
     │ npw-core（原生）    │ npw-core（WASM）  │ npw-core（WASM） │ npw-core（.so）     │
     │ SQLite 本地副本     │ IndexedDB 本地副本 │ 内存（不落盘）   │ SQLite 本地副本     │
     │ Hello / ssh-agent / │ 内容脚本：表单识别、 │                │ AutofillService /   │
     │ 快捷搜索 / 自动输入 │ passkey 拦截       │                │ CredentialProvider  │
     └────────────────────┴──────────────────┴────────────────┴────────────────────┘
                     ▲ 同一套 Rust 核心：加密、数据模型、同步与合并、网址匹配、导入导出、TOTP、passkey
```

原则：
- **核心只有一份**。加密、序列化、合并、匹配规则在所有端逐字节一致；各端只实现“界面”和“系统集成”。
- **核心不碰平台**：存储（SQLite / IndexedDB）、HTTP（原生 reqwest / 浏览器 fetch）、时间、随机数通过小接口注入；这样同一份核心能编译到 Windows、Android、WASM。
- **明文只在已解锁的客户端内存里**。

## 3. 仓库结构、版本与 CI

沿用 NyaRemoteControl 的做法：多个独立仓库克隆到同一父目录，共享 `target/`；`common` 不单独发版，各产品仓库发版时用 `COMMON_REF` 固定所用的 common 提交。

```
NyaPassword/
├─ common/    仓库 NyaPassword-common：Rust 核心 crate、共享 Web 界面、脚本、本文档
├─ server/    仓库 NyaPassword-server：服务端 + 网页版 + 管理后台 + 备份（Docker 镜像）
├─ desktop/   仓库 NyaPassword-desktop：桌面端（Tauri 2；Windows 为主，macOS / Linux 同时构建）
├─ chrome/    仓库 NyaPassword-chrome：浏览器扩展（Chromium 内核：Chrome、Edge）
├─ android/   仓库 NyaPassword-android：Android（Kotlin + Compose 界面，Rust 核心经 UniFFI）
├─ signing/   不属于任何仓库：Android 签名密钥、桌面更新签名私钥（备份到离线介质）
└─ target/    共享的 cargo 输出目录（各仓库 .cargo/config.toml 指向 ../target）
```

### 3.2 版本

- 每个产品仓库有 `VERSION`（`MAJOR.MINOR.PATCH[-PRERELEASE]`），与 Cargo.toml / package.json / manifest 保持一致；CI 检查一致性。`scripts/release.ps1 x.y.z` 改版本、写 `COMMON_REF`、提交、打 tag `vx.y.z`；推送 tag 后 GitHub Actions 构建并发布（带后缀的为预发布）。四个产品各自独立发版。
- 浏览器扩展的 `manifest.version` 只能是 1–4 段纯数字：预发布 `0.3.0-beta.2` → `version: "0.3.0.2"`、`version_name: "0.3.0-beta.2"`；正式版 `0.3.0` → `version: "0.3.0.1000"`、`version_name: "0.3.0"`。这样同一版本的正式版总排在它的预发布之后，浏览器才会从 beta 升到正式版（预发布序号须 < 1000，由 release-lib 换算和检查）。
- Android `versionCode = MAJOR*1_000_000 + MINOR*1_000 + PATCH`（同 NyaRemoteControl）。
- 除了产品版本，还有三个**兼容版本**，比产品版本更重要：

| 版本 | 位置 | 规则 |
|---|---|---|
| 条目格式 `FORMAT_MAJOR.MINOR` | `npw-model` | §5.6。发版时必须已冻结（schema + 加密样例），否则发版脚本拒绝 |
| 加密信封 `ENVELOPE_V` | `npw-crypto` | 密文头部 1 字节；新算法只能新增版本，旧版本永久可解 |
| API `API_MAJOR.MINOR` | `npw-api` | 同 MAJOR 内只增不改；新行为通过功能协商开启；冻结方式同上 |

### 3.3 CI（GitHub Actions）

CI 工作区与本地布局一致：产品仓库检出到 `<repo>/`，common 检出到旁边的 `common/`（CI 用 main，发版用 `COMMON_REF`）；`cargo test` 在 CI 不加 `--locked`（common main 可能比 Cargo.lock 新），发版加 `--locked`。

| 仓库 | ci.yml（push main / PR） | release.yml（tag `v*`） |
|---|---|---|
| common | fmt、clippy、`cargo test`（windows-2022 + ubuntu）；`wasm32` 构建 + wasm 测试（node）；`aarch64-linux-android` check；导入器模糊测试（每个 20 秒）；web：check、vitest、build；兼容样例测试 | 不发版 |
| server | 检查 VERSION；测试；构建 linux 二进制；`docker build` + 冒烟（`--version`、`--healthcheck`） | 检查 tag = `v<VERSION>`；`--locked` 测试；buildx 镜像（linux/amd64、linux/arm64）推到 `ghcr.io/<owner>/nyapassword-server`（tag、`MAJOR.MINOR`、`latest`，后两个预发布不打）；GitHub Release 附 `deploy/` 示例 |
| desktop | 矩阵 windows-2022 / macos-latest / ubuntu-24.04：测试、构建（不出安装包） | 同 NyaTunnel 客户端的矩阵：`NyaPassword_<版本>_x64-setup.exe`、`_windows_x64.zip`、`_macos_{arm64,x64}.dmg`、`_linux_x64.{AppImage,deb}`、`SHA256SUMS`、更新签名；macOS 版不做 Apple 公证（首次打开需在系统设置里放行） |
| chrome | npm ci、构建 WASM、类型检查、单元测试、Playwright（Chromium）加载扩展跑 `common/autofill` 测试页 | `NyaPassword-Chrome_<版本>.zip`（Chrome / Edge 商店共用）；先手动上传，稳定后用商店 API |
| android | 同 NyaRemoteControl：JDK 17、固定 NDK、cargo-ndk、`cargo test`、lint、单元测试、debug APK | 恢复签名密钥（`ANDROID_KEYSTORE_BASE64` 等四个 secret）→ `NyaPassword-Android_<版本>.apk` → `apksigner verify` → `.sha256` |

Actions 全部固定到提交哈希、`permissions: {}` 默认最小权限、`persist-credentials: false`、CI 并发取消 / 发版不取消（同现有项目）。

### 3.4 自更新与发布签名
沿用现有项目的方式（查 GitHub Releases `latest`、按命名选资产、校验 SHA-256），但**密码管理器额外要求签名**：SHA-256 和安装包放在同一个 Release 里，GitHub 账号被盗时两者可以一起被换掉，而被换掉的桌面端 / APK 能读到所有密码。因此：
- 桌面端更新包和服务端二进制用离线 minisign 私钥签名（私钥在 `signing/`，CI 用 secret），客户端内置公钥校验。
- Android 依赖 APK 签名本身（系统拒绝签名不同的更新），应用内再核对签名证书指纹。
- 浏览器扩展走商店更新，不做自更新。

## 4. 安全模型与加密

### 4.1 威胁模型

| 攻击者 | 能拿到 | 结果 |
|---|---|---|
| 备份存储商 / 备份泄露 | 备份文件 | 外层 age 加密挡住；即使拿到 age 私钥，里面也只有条目密文，且没有 Secret Key 无法暴力破解主密码 |
| 服务器被入侵（读数据库） | 全部密文、元数据（条目数、大小、时间） | 同上，无法离线破解 |
| 服务器被入侵（篡改） | 可以返回任意数据 | 密文用 AEAD + 关联数据绑定到“保险库 ID + 条目 ID”，无法替换 / 搬运；客户端记录已见过的最大修订号和序号，发现回滚则报警；**无法**阻止删除（靠备份和客户端副本恢复） |
| 网络中间人 | — | TLS；OPAQUE 不传输密码等价物 |
| 设备丢失（已锁定） | 本地副本 | 需要主密码；Secret Key 由系统密钥库保护 |
| 设备被植入恶意软件（已解锁） | — | 不在防护范围（任何密码管理器都防不住），只做最小化：明文驻留时间短、剪贴板自动清除 |
| 钓鱼网页 / 恶意 iframe / 冒名 App | — | 网址按 iframe 自己的源匹配；Android 校验包签名证书；内联菜单放在扩展源的 iframe 里防点击劫持 |

### 4.2 密钥层级

```
主密码 ─NFKD─► Argon2id(m=64MiB,t=3,p=4, salt) ─┐
                                                  ├─ XOR ─► HKDF ─┬─► AUK（账户解锁密钥）
Secret Key（128 位，只在设备上） ─► HKDF ───────────┘               └─► OPAQUE 输入（登录用）

AUK ──解密──► 账户密钥 AK（256 位随机）
               ├─ 账户 X25519 密钥对（私钥由 AK 加密）  ← 共享保险库时用 HPKE 给成员封装保险库密钥
               └─ 保险库密钥 VK（每个保险库一把）
                     └─ 条目密钥 IK（每个条目一把）
                           ├─ 条目内容（XChaCha20-Poly1305）
                           └─ 附件密钥 FK（每个附件一把，分块流式加密）
恢复码（可选，256 位）──► 另一份 OPAQUE 注册 + 另一份 AK 封装 → 忘记主密码时可重设
```

- 改主密码：只需重新封装 AK、重新注册 OPAQUE，条目不动。
- 每条目一把密钥：移动条目到别的保险库只需重新封装 IK，不重写内容。
- Argon2 参数随账户保存，可升级（下次解锁时重新派生）。
- 主密码做 Unicode NFKD 规范化，不去首尾空格（各端输入法可能给出不同的组合字符，这是跨平台常见坑）。
- Secret Key 格式：`A1-` + 账户短 ID + 26 位 Base32（含校验位），便于抄写；在新设备上可扫紧急恢复包上的二维码。

### 4.3 登录认证：OPAQUE

用 `opaque-ke`（RFC 9807，已审计）。服务端只存 OPAQUE 注册记录，登录全过程不传送任何可离线验证的哈希；登录成功后服务端签发设备会话（短期 access token + 可轮换 refresh token，绑定设备 ID）。登录失败限速、可选 IP 封禁；首个账户注册后关闭注册，之后用邀请码。

### 4.4 密文信封

```
[ver:1 字节][alg:1 字节][nonce:24 字节][ciphertext ‖ tag:16 字节]
AAD = "npw/item/v1" ‖ vault_id ‖ item_id ‖ format_major
```
附件：每 1 MiB 一块，nonce = 前缀 ‖ 块序号 ‖ 末块标志（STREAM 构造），AAD 含附件 ID，防截断、防重排。

### 4.5 本地解锁

- 首次登录后，设备保存 Secret Key（Windows：DPAPI；Android：Keystore 包装；扩展：`chrome.storage.local` 中用设备密钥包装）和加密的 AK。**离线也能用主密码解锁**。
- 生物识别：主密码解锁后，用系统密钥库中“需要生物识别才能使用”的密钥再包一份 AK。Android：BiometricPrompt + `setUserAuthenticationRequired` + 新增指纹即失效；Windows：Windows Hello（`KeyCredentialManager` 对固定挑战签名，签名派生包装密钥）。
- 规则（2026-10-05 确认，[加密规格.md](加密规格.md) §4.4、§4.5）：每 14 天必须在本机输入一次主密码（到期后生物识别和 PIN 暂停；时间戳与 PIN 材料一起受 DPAPI / Keystore 保护，改文件不能延长）；生物识别失效（新录入指纹、重置 Windows Hello）或在本机改主密码后要重新设置。“启动时可直接用生物识别解锁”默认开：重启后 14 天内可直接用生物识别。
- PIN（只做桌面端和 Android）：至少 4 个字符；`Argon2id(NFKD(PIN), 随机盐, 账户 KDF 参数)` 包装 AK，再由平台保护（桌面：Windows 凭据管理器 / DPAPI；Android：不可导出的 Keystore AES-GCM 密钥，有 StrongBox 用 StrongBox）；连续 5 次错误删除；重启后可用；“使用前需要验证”也可以用 PIN。
- 浏览器扩展：解锁后的 AK 放 `chrome.storage.session`（只在内存）；MV3 Service Worker 被回收后从这里恢复；浏览器关闭即失效。可“由桌面端解锁”（Native Messaging，配对后桌面端把 AK 封装到扩展的 P-256 公钥交给扩展，见 [威胁模型.md](威胁模型.md) §3.9.1）：桌面端已解锁则直接解锁；桌面端锁定时，扩展里的明确操作（打开弹窗、点输入框里的按钮）让桌面端弹出自己的解锁窗口（主密码 / 生物识别 / PIN），解锁后扩展跟着解锁；桌面端没运行则由 Native Messaging 宿主先启动它；没装或没配对才用主密码。扩展不做 PIN。
- 自动锁定：空闲 N 分钟、系统锁屏、休眠；剪贴板 90 秒后清除（Windows 设置“不进剪贴板历史、不上传云剪贴板”；Android 设置敏感内容标志）。

### 4.6 库选择
RustCrypto（`argon2`、`hkdf`、`sha2`、`chacha20poly1305`、`ed25519-dalek`、`x25519-dalek`、`p256`）、`hpke`、`opaque-ke`、`zeroize`、`age`。全部纯 Rust、可编译到 WASM 与 Android。不自己写任何原语。

## 5. 数据模型

### 5.1 层次

```
账户 ─┬─ 设备（多个，可吊销）
      └─ 保险库（个人 / 工作…；v1 成员只有自己，成员与角色的表结构预留给共享）
            └─ 条目（模板类型；字段、分区、网址、passkey、附件、标签）
                  └─ 修订（每次保存一个，只追加）
```

### 5.2 条目内容（加密前的明文 JSON）

```json
{
  "format": "1.0",
  "template": "login",
  "title": "GitHub",
  "favorite": true,
  "tags": ["工作/开发"],
  "fields": [
    { "id": "username", "label": "用户名", "kind": "text",      "purpose": "username", "value": "octocat" },
    { "id": "password", "label": "密码",   "kind": "concealed", "purpose": "password", "value": "…",
      "generator": { "length": 24, "sets": ["upper","lower","digit","symbol"] } },
    { "id": "otp",      "label": "一次性密码", "kind": "totp",  "purpose": "otp", "value": "otpauth://totp/GitHub:octocat?secret=…" },
    { "id": "f_7c1e",   "label": "恢复码", "kind": "concealed", "section": "s_recovery", "value": "…" }
  ],
  "sections": [ { "id": "s_recovery", "label": "恢复" } ],
  "urls": [
    { "id": "u1", "url": "https://github.com/login", "match": "domain" },
    { "id": "u2", "url": "androidapp://com.github.android", "match": "exact", "cert_sha256": ["…"] }
  ],
  "passkeys": [
    { "id": "pk1", "rp_id": "github.com", "credential_id": "…", "user_handle": "…", "user_name": "octocat",
      "alg": -7, "private_key": "<PKCS#8, base64>", "counter": 0, "discoverable": true, "created_at": 1759536000000 }
  ],
  "notes": "",
  "attachments": [ { "id": "a1", "name": "recovery.txt", "size": 1234, "mime": "text/plain", "blob": "sha256:…", "key": "…" } ],
  "history": [ { "field": "password", "value": "旧密码", "until": 1759536000000 } ],
  "autofill": { "auto_submit": false, "never": false },
  "created_at": 1759536000000,
  "updated_at": 1759536000000
}
```

要点：
- **字段 ID 稳定**：模板字段用固定 ID（`username`、`password`、`otp`…），自定义字段用随机 ID。合并、历史、导入映射都靠它。
- **`kind`（怎么存怎么显示）与 `purpose`（自动填充时是什么）分开**：任何字段都能声明用途，例如“手机号”是 `kind: phone` + `purpose: username`。1Password 里“用户名必须是那个固定字段”的限制没有了。
- **未知键保留**：核心只改自己认识的键，其他原样写回。旧客户端编辑新客户端写的条目不会丢东西。
- 时间统一 UTC 毫秒整数；文本 UTF-8 原样保存（不改换行符）。

### 5.3 字段类型（`kind`）

`text`、`multiline`、`concealed`（可加 `"multiline": true`，即**多行密文**：恢复码、私钥、助记词、证书等，默认遮挡、可整体显示 / 复制、按行复制）、`pin`（数字、可设长度，如 6 位支付密码）、`email`、`phone`、`url`、`date`、`month_year`（卡有效期）、`number`、`totp`、`address`（结构化）、`reference`（指向另一个条目，例如服务器条目引用 SSH 密钥条目）、`file`（指向附件）、`boolean`。

### 5.4 模板（与 1Password 不同的地方）

模板只决定“新建时默认有哪些字段、怎么排版”，条目可以随意增删字段。内置模板相对 1Password 的调整（已确认）：

- 任何模板都能加“多行密文”字段；登录模板的“恢复码”默认就是多行密文。

| 模板 | 字段 / 调整 |
|---|---|
| 登录 | 用户名 / 密码 / 一次性密码 / 网址（多个，每个可单独设匹配方式）/ passkey（多个）。用户名可以是手机号或邮箱，用途字段区分 |
| 银行卡 | 持卡人、卡号、有效期、CVV、**开户行、卡类型（借记/信用）、预留手机号、交易密码（6 位 pin）** |
| 银行账户（新增，国内常用） | 开户行 / 支行、账号、户名、**网银登录名、登录密码、支付密码、U 盾 / 证书密码** |
| 证件（拆开 1Password 的护照 / 驾照） | 证件类型（身份证 / 护照 / 驾照 / 港澳通行证 / 社保卡…）、号码、姓名、签发机关、有效期、照片附件 |
| 身份 | 姓名、手机、邮箱、地址（结构化，多个）——不再把证件号塞进身份 |
| SSH 密钥 | 私钥（OpenSSH 格式）、公钥、指纹、类型（**含 ECDSA**，1Password 不支持）、备注、agent 设置（每次使用确认 / 允许的主机） |
| 服务器 | 地址、端口、用户名、密码、引用 SSH 密钥条目 |
| API 凭据 / 数据库 / Wi-Fi / 软件许可 / 加密钱包（助记词）/ 安全笔记 | 常规 |

### 5.5 网址匹配方式

`domain`（可注册域名，默认）、`host`（完整主机名，含端口）、`starts_with`、`exact`、`regex`、`never`。另有全局 + 自定义“等价域名”（如 `taobao.com` / `tmall.com`）。Android 应用用 `androidapp://包名`，并记录签名证书 SHA-256，防止同包名的冒名 App；通过 Digital Asset Links 自动关联网站。规则全部在 `npw-match` 里，各端结果一致。

### 5.6 格式版本与兼容规则

- `format` = `MAJOR.MINOR`。MINOR 只允许**增加**可选键；键名、类型、含义永不修改，废弃的键继续可读。
- 客户端读到更高 MINOR：可编辑，未知键保留。读到更高 MAJOR：**只读**并提示更新客户端——宁可不能改，也不写坏。
- 升级不批量重写：条目在下次被编辑保存时才按新格式写入。
- 每个发布过的格式版本冻结：`format/history/vX.Y/` 的 schema + `tests/compat/vX.Y/` 的加密样例；CI 在原生、WASM、Android 目标上都解一遍。发版脚本检查冻结（同 NyaRemoteControl 的协议冻结做法）。

## 6. 服务端存储

SQLite（WAL），单文件，便于备份。主要表：

| 表 | 内容 |
|---|---|
| `accounts` | ID、登录名、OPAQUE 记录（主 + 恢复码）、KDF 参数与盐、加密的 AK、公钥 |
| `devices` | ID、账户、名称、平台、客户端版本、最后在线、吊销时间 |
| `sessions` | refresh token 哈希、设备、过期时间 |
| `vaults` / `vault_members` | 保险库；成员、角色、HPKE 封装的保险库密钥 |
| `item_revisions` | **只追加**：(vault_id, item_id, revision) 主键、封装的 IK、密文、内容哈希、格式 MAJOR、大小、写入设备、时间、`deleted`（回收站标志也是一个修订） |
| `items` | 每个条目的当前修订号（指针），便于快速列表 |
| `changes` | 每个保险库单调递增的 `seq` → (item_id, revision)；同步按 seq 拉取 |
| `ops` | 已处理的客户端操作 ID（幂等，重试不会重复写） |
| `attachments` | 附件 ID → blob 哈希、大小；blob 文件放 `data/blobs/ab/abcdef…`（内容寻址、不可变） |
| `audit_log` | 登录、新设备、导入、导出、清空回收站、备份结果 |
| `backup_runs` / `settings` | 备份记录、服务端设置（敏感值用 `data/server.key` 加密） |

保留策略：修订默认全部保留（密码库很小，1 万条目 × 100 个修订也就几百 MB）；可设“保留最近 N 个且至少 M 天”。回收站默认 30 天后可清空，**清空需要用户在客户端确认**，服务端不自动删除。

## 7. 同步协议

### 7.1 原则
1. 服务端决定顺序：每个保险库一个单调递增 `seq`；每个条目一个修订号。
2. 写入用乐观并发：客户端声明“我基于修订 N 修改”，不是最新就返回 409，绝不覆盖。
3. 合并在客户端做（只有客户端能解密），以字段为单位三方合并；真正冲突时**两份都保留**。
4. 所有写入幂等（客户端生成操作 ID；条目 ID 用客户端生成的 UUIDv7）。
5. 删除也是一个修订（进回收站），编辑与删除冲突时**编辑胜**（条目恢复）。

### 7.2 流程

```
拉取：GET /v1/vaults/{id}/changes?since=<seq>&limit=500
      → [{item_id, revision, seq, deleted, wrapped_key, ciphertext, hash}], next_seq
推送：POST /v1/vaults/{id}/items:batch
      [{op_id, item_id, base_revision, wrapped_key, ciphertext, hash}]   （导入时 atomic=true 整批成功或整批失败）
      → 每项 ok{revision, seq} | conflict{current_revision} | rejected{reason}
通知：WebSocket /v1/events → {vault_id, seq}（收到就拉取；断线时每 5 分钟轮询兜底）
校验：GET /v1/vaults/{id}/digest → SHA-256(按 item_id 排序的 item_id‖revision‖hash)
```

### 7.3 客户端本地状态
- `shadow`：每个条目“最后一次与服务端一致”的版本（三方合并的 base）。
- `outbox`：待推送的修改（持久化、加密），离线时累积，联网后按顺序推送。
- `max_seq` / 每条目最大修订：用于发现服务端回滚。

### 7.4 三方合并（base = shadow，local = 本地修改，remote = 服务端最新）
- 标量字段（按字段 ID）：只一方改了取改的一方；两方改成相同值无冲突；两方改成不同值 → **冲突**：字段取远端值，本地值放进条目的 `conflicts` 列表并标记“有冲突待处理”，界面里二选一或都保留。
- 集合（网址、标签、passkey、附件）：按 ID 做三方集合合并（各自的增删都生效）。
- 备注：两方都改 → 按行三方合并，失败时同字段冲突处理。
- 字段的增删：增删都生效；一方删一方改 → 保留修改。
- 合并结果作为新修订基于远端修订推送；被覆盖的值同时还在修订历史里。

### 7.5 一致性自检
- 每次同步后比较摘要，不一致则全量对账（拉取条目头列表逐条比较）。
- “密码库健康检查”：逐条解密 + 解析 + schema 校验，报告无法解密或格式异常的条目（升级后自动运行一次、之后每周一次）。
- 服务端每天 `PRAGMA integrity_check`，结果进管理后台和告警。

### 7.6 API 兼容
`GET /v1/server-info` 返回 API 版本和功能列表；客户端按功能开启新行为，不比较版本号。同 MAJOR 内只增不改；字段只增不删（同 NyaRemoteControl 协议规则）。

## 8. 备份与恢复

### 8.1 备份内容
一致性快照（SQLite `VACUUM INTO` / 在线备份 API）+ 附件 blob + `data/server.key` + 设置。数据库很小，**每次都做全量**；附件不可变，按哈希**增量**上传。

### 8.2 打包与加密
```
nyapassword-backup-<时间>-<seq>.tar.zst.age
  manifest.json   版本、时间、每个保险库的最大 seq、条目数、各文件 SHA-256
  db.sqlite3
  server.key
附件：blobs/<哈希>.age（单独对象，已有的不重复上传）
```
age 加密给**两个接收者**：
- 服务端自己的密钥：用于自动恢复演练。它只保护“存储商看到元数据”，服务器本身本来就持有这些数据，所以放在服务端不增加风险。
- 你的离线密钥（打印在紧急恢复包里）：服务器整个没了也能恢复。

### 8.3 目标
v1 支持两种，可同时配置多个：
- **阿里云 OSS**（opendal 的原生 OSS 服务；防删模式见 §8.4）。
- **WebDAV**（坚果云、NAS 自带的 WebDAV 等；WebDAV 做不到“只写不删”，所以靠保留多个版本 + 另一个目标兜底）。

建议两个都配：OSS 防删，WebDAV 放另一家。底层用 `opendal`，以后要加 S3 / COS / R2 / 本地目录只是加一个配置类型。

### 8.4 调度与保留
- 有变更时防抖 10 分钟后备份一次（最多每小时一次）；无变更每天也做一次（证明系统活着）。
- 保留：按祖父-父-子（默认最近 48 个、每天 30 天、每周 12 周、每月 24 个月）。
- **防删模式（推荐）**：给服务器的凭据只有 `PutObject` 权限，桶开版本控制 / WORM（OSS 合规保留策略、S3 Object Lock、R2 Bucket Lock），过期清理交给存储端生命周期规则。服务器被入侵也删不掉历史备份。此模式下服务端不执行保留清理，只提示需要配置的生命周期规则。

### 8.5 校验、演练与告警
- 上传后：取回对象，比较 SHA-256。
- 每周自动恢复演练：下载最新备份 → 用服务端密钥解密 → 在临时目录打开数据库 → `integrity_check` → 比对条目数和各保险库 seq 与线上一致 → 抽样检查附件存在。
- 管理后台显示：每个目标最后成功时间、最近一次自动校验（“备份校验”页）结果、“距上次手动恢复演练 N 天”；概览页的待处理清单列出缺少的目标、离线恢复密钥、告警通道、失败或过期的备份 / 校验、未开启的管理员 TOTP、超过 90 天的手动演练。
- 离线恢复密钥在管理后台“恢复密钥”页用浏览器生成（私钥不经过服务器），打印 / 下载后确认才登记公钥；也可以粘贴已有的 `age1…` 公钥。
- 失败或超过 26 小时没有成功备份：通知（Webhook、邮件、Telegram、Bark）。

### 8.6 恢复
- `nyapassword-server restore --from <目标> [--at <时间>] --identity <离线私钥文件>`：恢复到新数据目录，打印 manifest 摘要，确认后切换。
- 管理后台可浏览备份列表、做“试恢复”（到临时目录，不影响线上）。
- **客户端离线导出（与服务端无关的逃生通道）**：桌面端可设定期（默认每周）导出到本地文件夹：①原生加密导出（无损，用主密码 + Secret Key 解锁）；②KDBX 4（KeePassXC 直接打开，含 TOTP、passkey、附件、SSH 密钥）。即使服务端、备份、甚至这个软件都不在了，数据仍可读。

## 9. 导入、导出与迁移

### 9.1 流程（所有来源相同）
```
解析 → 统一中间格式 → 映射到模板（无法对应的字段一律放进“其他字段”分区，不丢）
     → 预览：按类型计数、每条的映射方式、警告列表（重复、无法识别、超大附件）
     → 写入为一个导入批次（atomic，带标签“导入 2026-10-04 Bitwarden”）
     → 报告；一键撤销整个批次（进回收站）
```
导入后自动做一次逐条比对（导入源字段 vs 解密后的结果），报告必须 100% 对得上。

### 9.2 来源
| 来源 | 格式 | 说明 |
|---|---|---|
| Bitwarden / Vaultwarden | `.zip`（含附件）、JSON、加密 JSON（密码保护）、CSV | **第一优先**。移植 `bw2op` 的映射；文件夹 → 标签（嵌套）；**passkey（fido2Credentials）完整导入**；密码历史；自定义字段；SSH 密钥 |
| 1Password | `.1pux`、CSV | 分区、字段类型、标签、附件、TOTP |
| KeePass / KeePassXC | KDBX 4、CSV | 分组 → 标签；KeePassXC passkey 属性 |
| Chrome / Edge / Google 密码管理器 | CSV | |

passkey 能否迁移取决于导出方：Bitwarden 的 JSON / zip 导出带 passkey 私钥，可以完整迁移；1Password 和 Google 的导出文件据目前了解不含 passkey（需实测确认），这些网站要重新添加 passkey，导入报告会列出来。Android 上的 CXP 直接迁移不做（§1）。

### 9.3 导出
原生加密（无损）、KDBX 4、CSV（明文，需输入主密码二次确认并提示风险）。

## 10. 各端设计与兼容要点

### 10.1 共享核心的编译目标

| 目标 | 用于 | 注意 |
|---|---|---|
| `x86_64-pc-windows-msvc` | 桌面 | `+crt-static`（同现有项目） |
| `aarch64/x86_64-apple-darwin`、`x86_64-unknown-linux-gnu` | 桌面（macOS、Linux） | CI 构建与测试 |
| `x86_64/aarch64-unknown-linux-musl` | 服务端 Docker | 静态链接，镜像用 distroless / scratch |
| `aarch64/x86_64-linux-android` | Android | cargo-ndk，NDK 版本固定；UniFFI 生成 Kotlin |
| `wasm32-unknown-unknown` | 扩展、网页版 | `getrandom` 用 JS 后端；Argon2 64 MiB 在 WASM 里约 1 秒，需在扩展里实测；不能用线程 |
| `aarch64-apple-ios` | iOS（不做） | 核心和 UniFFI 结构上支持，需要时再说 |

### 10.2 共享界面（common/web）
Svelte 5 + Vite + TS，桌面、扩展完整页、网页版共用一套组件；Android 用 Compose 另写界面（自动填充和凭据提供程序都需要原生，且原生体验更好）。界面通过 `CoreBridge` 调核心：桌面走 Tauri 命令（原生核心，Argon2 更快），扩展 / 网页走 WASM。中文优先，i18n 预留英文。跟随系统浅色 / 深色。

### 10.3 桌面端（Tauri 2：Windows 为主，macOS / Linux 同时构建）
- 三栏主界面、托盘、开机启动到托盘、单实例。
- Windows Hello 解锁；锁屏 / 休眠自动锁定（WTS 会话通知）。
- **快捷搜索 + 自动输入**（Windows 上没有系统级自动填充接口）：全局快捷键（默认 `Ctrl+Shift+Alt+Space`）弹出搜索框，按前台窗口标题 / 进程匹配条目，选中后用 `SendInput` 输入（KeePass 式序列：`{USERNAME}{TAB}{PASSWORD}{ENTER}`）。
- SSH agent：监听 `\\.\pipe\openssh-ssh-agent`（被系统 OpenSSH Authentication Agent 服务或其他程序的 agent 占用时，应用内检测并显示占用者，引导停用或改用其他管道名 + `SSH_AUTH_SOCK`）；每次签名弹窗确认（可按会话记住）；Git 提交签名（SSHSIG）；WSL / Git Bash 的桥接说明。
- 浏览器扩展桥：Native Messaging 宿主（注册表 `HKCU\Software\{Google\Chrome,Microsoft\Edge,Chromium}\NativeMessagingHosts`；宿主就是桌面端程序本身，以宿主模式转发到正在运行的应用），配对确认后让扩展跟随桌面端解锁 / 锁定。
- passkey：Windows 11 第三方 passkey 插件接口（较新，待验证）。
- 剪贴板：不进剪贴板历史、不上传云剪贴板。
- 自动更新：GitHub Releases + SHA-256 + minisign 签名校验（§3.4）。
- 平台相关代码集中在 `desktop/src-tauri/src/platform/{windows,macos,linux}`，同一组 trait（解锁、密钥保存、全局快捷键、自动输入、ssh-agent 监听、剪贴板、浏览器桥注册）。macOS / Linux 与 Windows 同时实现、CI 构建和单元测试，但没有实机测试，发布时标“实验性”：

| 能力 | Windows | macOS | Linux |
|---|---|---|---|
| 生物识别 | Windows Hello | Touch ID（LocalAuthentication + 钥匙串） | 无（主密码；Secret Service 保存 Secret Key） |
| Secret Key 保存 | DPAPI | 钥匙串 | Secret Service（GNOME 钥匙圈 / KWallet） |
| ssh-agent | `\\.\pipe\openssh-ssh-agent` | Unix socket（`SSH_AUTH_SOCK`） | Unix socket |
| 自动输入 | SendInput（`KEYEVENTF_UNICODE`） | 计划 CGEvent（需辅助功能权限），暂未实现，只能复制 | 计划 X11，暂未实现，只能复制；Wayland 下不可用 |
| 浏览器桥 | 注册表 | `~/Library/Application Support/<浏览器>/NativeMessagingHosts` | `~/.config/<浏览器>/NativeMessagingHosts` |
| passkey 系统集成 | Windows 11 插件（待验证） | 不做 | 不做 |

### 10.4 浏览器扩展（MV3）
- 只做 Chromium 内核（Chrome、Edge，同一个包）。框架 WXT（Vite），界面 Svelte 共享组件，核心 WASM 跑在 Service Worker。WXT 本身支持 Firefox，以后有需要只是多一个构建目标。
- 独立工作（不依赖桌面端），有桌面端时可由桌面端解锁。
- **表单识别**（最花时间的部分）：`autocomplete` 属性、type、name / id / label / placeholder 关键词（中英文，词表在 `common/autofill`）、表单结构、Shadow DOM、所有 frame、SPA（MutationObserver）、分步登录（先用户名后密码）、手机号 + 短信验证码登录（只填手机号）。
- **按 frame 自己的源匹配**，跨域 iframe 里的登录框要提示用户；顶层页和 iframe 不同源时默认不自动填。
- 内联菜单渲染在扩展源的 iframe 里（页面脚本读不到），检测遮挡 / 透明度防点击劫持。
- 填写：用原生 setter 赋值 + 派发 input / change 事件（兼容 React / Vue）；可选填完自动复制 TOTP。
- 保存 / 更新提示：监听提交、导航、fetch 结果；可选关闭浏览器自带的保存密码。
- passkey：MAIN world 脚本接管 `navigator.credentials.create/get`，经扩展消息交给 `npw-passkey`；用户可选“用设备 / 安全密钥”回落到原生实现。
- 银行卡、身份（姓名、手机、地址）表单识别与填写（国内地址按省 / 市 / 区 / 详细地址拆分）。
- 分发：Edge 外接程序商店（免费）、Chrome 网上应用店（可设为“不公开”）。Windows 版 Chrome 不允许安装商店外的 crx，只能开发者模式加载。

### 10.5 Android（Kotlin + Compose + Rust 核心）
- 结构同 NyaRemoteControl Android：Gradle 用 cargo-ndk 构建核心（arm64-v8a、x86_64），UniFFI 生成 Kotlin 绑定。`applicationId = app.nya.password`，minSdk 26，targetSdk 36。
- **AutofillService**：解析 AssistStructure（应用看 autofillHints / id / hint；浏览器看 webDomain），锁定时返回需要认证的数据集（解锁后填充）、Android 11+ 输入法内联建议、SaveInfo 保存新密码。Chrome 需要在 Chrome 设置里打开“使用其他服务自动填充”，应用内做引导。
- **CredentialProviderService**（Android 14+）：密码和 passkey 都走系统凭据管理器界面。
- 应用 ↔ 网站：Digital Asset Links + 用户手动关联，记录签名证书。
- 生物识别、`FLAG_SECURE`、剪贴板敏感标志、自动锁定。
- 国内 ROM（HyperOS、ColorOS 等）：自动填充设置入口路径不同、后台限制、部分 ROM 的凭据管理器可能被精简——在你的手机上实测，做设置引导页。
- 自更新：检查 GitHub Releases（同 NyaRemoteControl）。

### 10.6 服务端
- Rust（axum + tokio + rusqlite）。选 Rust 而不是 Go：与客户端共用 `npw-api` 类型、OPAQUE 实现（跨语言的 OPAQUE 实现之间互通有风险）和备份格式。
- 只提供 Docker 部署（linux/amd64、linux/arm64）。
- 单二进制 + `data/` 目录 + `config.toml`（`NYAPASSWORD_*` 环境变量可覆盖）；网页版和管理后台构建后嵌入二进制（`rust-embed`），数据库迁移脚本也嵌入。
- 只监听 `127.0.0.1`，TLS 由 Caddy 负责（同 NyaTunnel）。
- 部署（同 NyaTunnel 服务端）：`deploy/docker/` 下 `docker-compose.yml`（镜像版本取自 `.env`、`read_only`、`no-new-privileges`、`./data` 卷、日志轮转）、`docker-compose.build.yml`（本地构建覆盖）、`.env.example`、`entrypoint.sh`；`deploy/caddy/Caddyfile`。Dockerfile 多阶段：node 构建 web → Rust（musl）构建 → alpine 运行（非 root、`HEALTHCHECK` 用 `--healthcheck`）。示例域名一律 `example.com`。
- 管理后台：账户与设备、备份目标 / 记录 / 演练、审计日志、健康状态、邀请码。管理员需要单独的管理口令 + TOTP。

### 10.7 跨平台一致性清单
| 问题 | 处理 |
|---|---|
| 主密码 Unicode 组合形式不同 | NFKD |
| 时间 | UTC 毫秒整数；TOTP 依赖时钟，客户端与服务端时间差 > 30 秒时提示 |
| 网址匹配、公共后缀表、等价域名 | 全部在 `npw-match`；公共后缀表随核心版本更新 |
| 序列化细节（键顺序、浮点、转义） | 只有核心读写条目 JSON；内容哈希对密文计算，不依赖 JSON 规范化 |
| 换行符 | 原样保存；导出 CSV 时统一 CRLF |
| 文件名 / 路径（附件） | 附件名原样保存，落盘时按平台规则清理 |
| WebView 差异（WebView2 / WKWebView / WebKitGTK） | 共享界面只用 Baseline 2024 范围内的 Web 特性；CI 跑 Playwright（Chromium + WebKit），macOS / Linux 版靠这个兜底 |
| 中文搜索 | 拼音 / 首字母索引在核心里生成，各端结果一致 |
| 表单识别 Kotlin / TS 两份实现 | 共用 `common/autofill` 的词表和测试页，两边跑同一批用例 |

## 13. 已确认的决定（2026-10-04）

1. 模板按 §5.4：国内银行卡 / 银行账户（支付密码、U 盾）、证件单独成类、手机号可作用户名；另加**多行密文**字段（恢复码等）。
2. v1 只做单账户；密钥层级、数据表、API 预留共享。
3. 使用 Secret Key（§4.2）。新设备首次登录时输入或扫紧急恢复包上的二维码，之后这台设备记住它。
4. 浏览器只做 Chromium 内核（Chrome、Edge），目录名 `chrome`；Firefox 不做。
5. 桌面端 Windows、macOS、Linux 一起做；macOS / Linux 不做实机测试，标“实验性”。
6. 服务端只提供 Docker 部署（amd64、arm64 都出镜像）；备份目标为阿里云 OSS + WebDAV。
7. Android 上的 CXP 直接迁移不做；迁移走电脑端文件导入。
